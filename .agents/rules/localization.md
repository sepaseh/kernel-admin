# Local translation catalogs

The standalone admin owns src/shared/i18n. Each locales/<code>.ts is the only message catalog for that language, as a flat Record<string, string> with all labels at the root. catalogs.ts registers those objects directly; index.ts initializes i18next and date.ts initializes date vendors. Do not add common.ts/admin.ts catalogs, per-language folders or compatibility reexports. Catalog data modules remain pure and do not import React, i18next, Day.js or runtime adapters. Persian calendar data stays separate in dayjs/fa.ts because it is calendar adapter data, not UI messages.

All ten codes in locales.ts require a genuine, complete code-named file with the current 111 root messages, such as locales/fa.ts or locales/en.ts. Reuse an existing semantic root key inside that catalog before adding copy, and remove superseded aliases. Never use empty catalogs, English spreads or English placeholder copies as translations. Preserve i18next {{variable}} placeholders, key parity, file/registry agreement and the Persian bootstrap fallback. User-entered data is not translation data.

Imports inside the adapter use local ./ modules; other frontend modules use @/shared/i18n paths. No shared translation package or catalog dependency on another repository exists. Changes are owned here; wire language codes must remain compatible with API settings. Public API settings are the sole language authority before and after authentication. i18next and Core start with fixed fa; loading failure stays retryable and later refresh failure retains the last verified settings. Ignore legacy localStorage language values and storage events without reading, writing or deleting them. Core exposes no language setter; i18next, Ant Design and Day.js follow its API-derived language. Window focus reloads public settings so returning tabs learn backend changes. Only system super-admins see the settings language chooser. Ordinary settings.update saves omit languageCode while preserving theme/logo rights; API authorization remains authoritative. Theme/compact persistence and cross-tab synchronization stay intact.

Validate language metadata at the settings HTTP boundary. Supported regional codes normalize to the registered base code while preserving server direction, calendar, name and nativeName. Unsupported/malformed metadata rejects with localized error feedback rather than silently substituting a local language. Core keeps the complete validated language object. Ant Design and document.dir use its direction; Day.js and Calendar use its calendar, mapping only the vendor spelling gregorian to gregory. Local code maps may select vendor locale modules; they cannot choose direction or calendar. Fixed fa/rtl/jalali metadata is bootstrap only. Calendar values/labels must apply metadata explicitly and reset a retained date instance when its calendar changes; persisted calendar date keys remain Gregorian YYYY-MM-DD.

The date.ts runtime adapter registers the real vendor locales and supplies their Jalali month names through Intl Persian-calendar formatting. Keep Gregorian Persian months distinct from jmonths in pure dayjs/fa.ts. Both calendars must format with all ten loaded vendor locales, including en-gb, rather than relying on an unregistered locale falling back to en in tests.

Run the affected runtime tests through the published unit coverage command, typecheck and the relevant isolated Storybook browser checks. `test:i18n` is not a published script in this phase. The integrity gate checks complete flat key and placeholder parity, canonical catalog object propagation, removed duplicates, calendar data, pure data imports and exactly ten code-named message files.
