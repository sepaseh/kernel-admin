# پیش‌نیازهای میزبانی با Docker

[English](README.md) · [فارسی](README.fa.md)

این پوشه تعریف Docker و Compose و ابزار smoke با مالکیت مشخص منابع را فراهم می‌کند. منابع پذیرفته‌شده و `applicationReady` را از [سیاست انتشار](../../.github/bootstrap-policy.json) و دستورها را از [فهرست اعتبارسنجی](../../.agents/validation.json) بخوانید. تا وقتی آمادگی false است، این پیش‌نیازها پنل قابل اجرا را اثبات نمی‌کنند. image واقعی علاوه بر آن به ورودی و تنظیمات ساختِ پذیرفته‌شدهٔ برنامه و مسیر ثبت‌شدهٔ بسته‌بندی نیاز دارد. وجود تعریف image، واردکردن ابزار یا آزمون ساختگی چرخهٔ منابع، شاهد ساخت موفق image یا اجرای واقعی smoke نیست.

هدف این image ارائهٔ فایل‌های ایستای ادمین با Nginx است؛ اجرای احراز هویت، داده و ذخیره‌سازی در اختیار API مستقل می‌ماند. تنظیمات عمومی ساخت و نمونهٔ ساختگیِ بازبینی‌شده راز نیستند. گواهی و کلید واقعی اپراتور باید خارج از Git و زمینهٔ ساخت بمانند و پس از فعال‌سازیِ دارای مجوز، فقط‌خواندنی متصل شوند.

فرایند ارائهٔ فایل با کاربر `nginx` همان image و درگاه‌های داخلی HTTP و HTTPS برابر ۸۰۸۰ و ۸۴۴۳ اجرا می‌شود. Compose درگاه‌های عمومی انتخاب‌شده را به این درگاه‌های داخلی متصل می‌کند و همهٔ قابلیت‌های لینوکس را حذف می‌کند. فایل PID و فایل‌های موقت Nginx در اتصال قابل‌نوشتن `/tmp` قرار دارند؛ باقی فایل‌سیستم ریشه فقط‌خواندنی می‌ماند. کلید خصوصی TLS باید بدون خواندنی‌شدن برای همه، در دسترس همان کاربر باشد و پوشه‌های والد اجازهٔ عبور بدهند. مالکیت و مجوزها را خارج از image تنظیم کنید؛ کلید اپراتور را هرگز وارد ساخت نکنید.

سازندهٔ گواهی موقت ابزار smoke فقط برای ایجاد کلید متعلق به همان اجرا و واگذاری آن به `nginx`، صریحاً با کاربر root اجرا می‌شود؛ پوشهٔ موقت خودش را قابل‌عبور و کلید را فقط برای مالک و گروه خواندنی می‌کند. کانتینر ارائهٔ فایل از کاربر بدون امتیاز image، اتصال فقط‌خواندنی گواهی و بدون قابلیت‌های لینوکس استفاده می‌کند. تلاش‌های پیاپی آمادگی به ۶۰ درخواست سند و ۴۵ بررسی سلامت محدود می‌مانند و لغو میان تلاش‌ها بررسی می‌شود. آزمون‌های ساختگی پایان تلاش‌ها و پاک‌سازی را پوشش می‌دهند؛ این شواهد به معنی اجرای واقعی کانتینر نیست.

ابزار smoke و [مالک منابع](resources.mjs) از نام و برچسب یکتا، تگ دقیق image، builder اختصاصی و پوشهٔ موقتِ تأییدشده استفاده می‌کنند. آزمون‌های ساختگی، راهبری و پاک‌سازی در خطا را بدون راه‌اندازی Docker بررسی می‌کنند. اجرای واقعی علاوه بر ساخت کامل برنامه، به موتور محلیِ مجاز و Buildx نیاز دارد. همهٔ پاک‌سازی‌های متعلق به همان اجرا باید امتحان شوند و خطای اصلی و خطای پاک‌سازی حفظ شوند. قطع موتور یا پایان غیرقابل‌مهار فرایند ممکن است پاک‌سازی دستی همان منابع مشخص را لازم کند. image، volume یا cache مشترک را prune نکنید و builder منتخب سراسری را تغییر ندهید.

پیش از عملیات آیندهٔ دارای مجوز، [استقرار](../../docs/deployment.fa.md) و [بازگشت نسخه](../../docs/release-operations.fa.md) را بخوانید.
