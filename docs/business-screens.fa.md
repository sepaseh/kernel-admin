# صفحه‌های مدیریتی و فرم‌های محافظت‌شده

[English](business-screens.md) · [فارسی](business-screens.fa.md)

ماژول‌های حساب، کاربران، نقش‌ها، تنظیمات، تقویم و داشبورد بر [زیرساخت Core و احراز هویت](core-auth.fa.md) بنا می‌شوند. داشبورد قاب چیدمان فراهم می‌کند و شاخص مدیریتی پیاده نمی‌کند. مالکیت تغییر داده، مجوز، نسل درخواست و زبان تنظیمات در ادامه، مستقل از مرحلهٔ انتشار معتبر است.

پیش از ادعای ترکیب یا آمادگی برنامه، [سیاست انتشار](../.github/bootstrap-policy.json) و [دروازهٔ کامل مرجع](../.agents/validation.json) را بخوانید. تا وقتی `applicationReady` برابر false است، ماژول جداگانه و [محیط مستقل Storybook](storybook-verification.fa.md) ساخت production، مسیر کامل برنامه یا مقایسهٔ تصویری تأییدشده را ثابت نمی‌کنند.

## مالکیت تغییر داده

هوک `useMutationRequest` قصد عملیات را پیش از کار ناهمگام ثبت و درخواست دوم در
حال انتظار را رد می‌کند. کار به مصرف‌کنندهٔ نصب‌شده، شناسهٔ منطقی، مجوز و نسل
توکن وابسته است. تغییر شناسه یا مجوز، لغو صریح و جداشدن از درخت نمایش، عملیات را
نامعتبر می‌کنند. لغو به آداپتر HTTP می‌رسد؛ حتی آداپتری که لغو را نادیده بگیرد
نمی‌تواند نتیجهٔ قدیمیِ قابل‌پذیرش برگرداند. callback باقی‌مانده از رکورد یا نشست
قبلی نیز نمی‌تواند کار تازه‌ای شروع کند.
مالکیت فقط در layout effect مربوط به تغییر قطعی رابط عوض می‌شود؛ رندر تعلیق‌شده
یا کنارگذاشته‌شده عملیات متعلق به صفحهٔ هنوز قابل‌مشاهده را نامعتبر نمی‌کند.

خروجی `run` برای پاسخ پذیرفته‌شده یک شیء است، حتی وقتی پاسخ موفق void باشد.
مصرف‌کننده درست پیش از ثبت داده، پیام موفقیت عادیِ متعلق به همان مؤلفه یا
جابه‌جایی مسیر،
`result?.isCurrent()` را بررسی می‌کند؛ لغو یا درخواست تازه می‌تواند پس از تکمیل
Promise رخ دهد. خطای فعلی به فرم مالک می‌رسد و لغو پیام خطای عمومی نمی‌سازد.
هوک تغییر داده را تکرار نمی‌کند؛ کلاینت HTTP می‌تواند درخواست تغییر محافظت‌شده را
پس از ۴۰۱ و refresh موفق در همان نسل ورود فقط یک‌بار تکرار کند. خطای گذرای تغییر
داده باعث تکرار خودکار نمی‌شود. لغو سمت کاربر تغییر ثبت‌شدهٔ سرور را برنمی‌گرداند.
خطا مقدار اصلی را در `cause` حفظ می‌کند. مصرف‌کننده پیش از نمایش پیام از
`error.cause`، شرط `isCurrentMutationError(error)` را می‌سنجد؛ عملیات می‌تواند بین
ردشدن Promise و catch مصرف‌کننده قدیمی شود.

قصد درخواست رمز ایمیل حساب پیش از اعتبارسنجی ناهمگام ثبت می‌شود. تغییر ایمیل،
تأیید معلق را نامعتبر و رقم‌ها و شمارندهٔ قبلی را پاک می‌کند. پاسخ پروفایل، نام
کاربری و تأیید ایمیل فقط فیلدهای متعلق به همان عملیات را به‌روز می‌کنند؛ تکمیل
وارونهٔ پاسخ کامل حساب، تغییر مستقل پذیرفته‌شده را حذف نمی‌کند. تغییر گذرواژه
نمی‌تواند ورود جدیدتر را پاک کند.

فرم کاربران و نقش‌ها مجوز ساخت یا ویرایش را هنگام بازشدن و ارسال بررسی می‌کند،
حتی در ورود مستقیم با hash. بستن کشو، تعویض رکورد یا نشست ادامهٔ عملیات قدیمی را
نامعتبر می‌کند. منو و کنترل غیرفعال برای نمایش هستند؛ API جداگانه باید هر عملیات
را مجاز بشمارد. فیلتر کاربران تأخیر ۵۰۰ میلی‌ثانیه‌ای را حفظ و تایمر معلق را هنگام
جداشدن پاک می‌کند.

گذرواژهٔ تولیدشدهٔ کاربر یک نتیجهٔ مشخصِ تأییدشده است: پس از تکمیل موفق درخواست
ساخت کاربر یا بازنشانی گذرواژه، عملیات آغازکننده رمز را نگه می‌دارد و با اعلان
سطح برنامه در همان نسل ورود نمایش می‌دهد، حتی اگر مؤلفه جدا، محدوده عوض یا عملیات
لغو شده باشد. با تغییر نسل ورود، این اعلان نمایش داده نمی‌شود. به‌روزرسانی قدیمی
فرم، جابه‌جایی مسیر و پیام خطای عادی همچنان به حفاظت چرخهٔ عملیات وابسته‌اند.
پاسخ HTTP لغوشده یا ناموفق مشخص نمی‌کند که سرور رمز را اعمال کرده است یا نه و
نباید موفقیت قطعی اعلام شود.

تنظیمات، مالکیت زبان، جهت، تقویم و پالت در API را حفظ می‌کند. فقط مدیر کل تغییر
زبان را در بدنه می‌فرستد و تنظیمات پذیرفته‌شده خواندن قدیمی Core را کنار می‌زند.
حذف یا تعویض لوگوی در حال ارسال، پیش از پاک‌کردن شناسه، آپلود را نامعتبر می‌کند.
کنترل آپلود و رمز یک‌بارمصرف نام ترجمه‌شدهٔ دسترس‌پذیر دارند. تغییر تقویم نیز از
همین چرخه استفاده می‌کند و بدنهٔ تاریخ API و تلاش دوبارهٔ خواندن را حفظ می‌کند.

## محدودهٔ اعتبارسنجی

فهرست دقیق، مالکیت وابستگی ماژول‌های محصول و پوشش اندازه‌گیری‌شده همراه این
ماژول‌ها گسترش می‌یابد. تمام بررسی‌های الزامی رسمی و آستانه‌های موجود الزامی می‌مانند.
آزمون‌های واقعی React و Ant Design در jsdom جداگانه و HTTP مصنوعی با پاسخ‌های
بسته در برابر درخواست ناشناخته اجرا می‌شوند. پشتیبان آزمون به checkout دیگری
وابسته نیست. پروژهٔ جداگانهٔ Storybook از mock کامل مالکان API ساختگی و Chromium
واقعی استفاده می‌کند؛ راه‌اندازی برنامه را اجرا نمی‌کند و جای پوشش اندازه‌گیری‌شدهٔ
واحد و قواعد مخزن را نمی‌گیرد.

این آزمون‌ها پنل اجرایی یا رفتار API بیرونی را ثابت نمی‌کنند. مرحلهٔ برنامه باید
پیش از ادغام هر نوزده بررسی واقعی الزامی، از جمله ساخت نهایی، مسیر مرورگر و
بررسی بصری را اجرا و پاس کند. [قابلیت اطمینان درخواست](admin-request-reliability.fa.md)،
[اعتبارسنجی ورودی](input-validation.fa.md) و [سیاست انتشار](bootstrap.fa.md) را ببینید.
