# قابلیت اطمینان درخواست‌های پنل

[English](admin-request-reliability.md) · [فارسی](admin-request-reliability.fa.md)

به‌روزرسانی محدوده: ۲۷ اکتبر ۲۰۲۶. مرحلهٔ غیرقابل اجرای `storybook-verification` آداپتورهای
HTTP متعلق به قابلیت‌ها، هوک‌های درخواست، ارائه‌دهنده‌های Core و Ant Design،
فرم‌های احراز هویت، صفحه‌های مدیریتی، ماژول‌های چیدمان و کارگاه جداگانهٔ Storybook
با تعامل واقعی مؤلفه‌ها و بررسی دسترس‌پذیری در Chromium را منتشر می‌کند. مقدار
`applicationReady` همچنان false است؛ نقطهٔ ورود برنامه، ترکیب متصل App و Routes،
ساخت نهایی برنامه، مسیر سرتاسری کامل برنامه یا بررسی بصری منتشر نمی‌شود.
هوک‌های کوچک خواندن عمر درخواست را هماهنگ
می‌کنند؛ کتابخانهٔ query، دسترسی فرانت‌اند به دیتابیس یا تکرار سرویس کسب‌وکار اضافه نشده است.

## محدودیت زمان و تلاش مجدد

- درخواست معمول Axios و درخواست جداگانهٔ refresh مبتنی بر کوکی، به‌صورت پیش‌فرض
  برای **هر تلاش ۱۵ ثانیه** فرصت دارند. بارگذاری فایل صریحاً **۶۰ ثانیه** فرصت دارد.
  این محدودیت هر درخواست است، نه بودجهٔ ۱۵ثانیه‌ای برای کل خواندن، refresh و تکرار.
  عملیات طولانی‌ترِ تازه باید سیاست آگاهانهٔ خودش را داشته باشد.
- پاسخ **۴۰۱** محافظت‌شده با شناسهٔ نسل زمان ارسال، همان رفتار موجودِ یک refresh
  و یک تکرار را در همان نشست حفظ می‌کند، از جمله برای درخواست تغییر واجد شرایطی
  که لغو نشده است. خطای احراز هویت عمومی یا خواندن عمومی GET/HEAD /settings باعث
  refresh نمی‌شود؛ PUT /settings محافظت‌شده است. خطای ۴۰۱ بدون config درخواست یا
  نسل مبدأ، بدون refresh یا انقضای ورود فعلی به خطای معمول تبدیل می‌شود؛ اعتبارنامهٔ فعلی مالک آن درخواست
  را مشخص نمی‌کند. خطای شبکه، timeout، پاسخ ۴۲۹
  یا ۵xx باعث تکرار خودکار درخواست نمی‌شوند.
- خواندن‌های هم‌زمان یک نشست، یک refresh مشترک دارند. لغو یک خواندن انتظار همان
  مصرف‌کننده را متوقف می‌کند و refresh دیگران را لغو نمی‌کند. ورود تازه، refresh
  خودش را دارد و شکست refresh قدیمی را به ارث نمی‌برد.
- شکست موقت refresh قابل‌تلاش‌مجدد می‌ماند؛ پاسخ ۴۰۱ یا ۴۰۳ refresh نشست فعلی یا ۴۰۱ دوم، نشست
  محلی را منقضی می‌کند. Layout حساب هنگام بررسی نشست یا خطای موقت، محتوای
  محافظت‌شده را نشان نمی‌دهد.
- timeout، خطای HTTP و خطای شبکه پیام مفید دارند. خطای HTTP وضعیت، علت اعتبارسنجی
  و شناسهٔ معتبر درخواست را حفظ می‌کند. لغو عمدی toast خطای قابلیت ایجاد نمی‌کند.

## مالکیت خواندن و وضعیت قابل‌مشاهده

فایل `shared/hooks/useReadResource.ts` خواندن خودکار و `reload` صریح را مدیریت
می‌کند. یک loader پایدار بفرستید: تابع واردشده از ماژول یا `useCallback` برای
آرگومان وابسته به فیلتر، با ورودی `AbortSignal`. فایل `useReadRequest.ts` برای
خواندن جزئیات در پاسخ به رویداد است. هر دو کار قدیمی را لغو و ثبت نتیجه را با شمارهٔ
درخواست و وضعیت mount کنترل می‌کنند، حتی اگر adapter به لغو توجه نکند. لغو صریح
حالت مشغول را بدون نیاز به شروع درخواست جایگزین پایان می‌دهد.

خواندن تنظیمات Core و بررسی حساب در چیدمان اصلی منتشرشده از این هوک‌ها استفاده
می‌کنند. تغییر loader دادهٔ قبلی را کنار می‌گذارد؛ بازخوانی همان منبع آخرین نتیجهٔ
موفق را نگه می‌دارد. تست loader ساختگی ترتیب معکوس تکمیل، کار قدیمی، unmount و
پاک‌سازی StrictMode توسعه را پوشش می‌دهد. ماژول‌های کاربران، نقش‌ها، تقویم و
تنظیمات اکنون از این خواندن‌های محافظت‌شده استفاده می‌کنند؛ آزمون واقعی React و
jsdom آن‌ها با اتصال واقعی API و مرورگر یکسان نیست.

کامپوننت `shared/ui/request-feedback` شکست اولیه و شکست بازخوانی را جدا می‌کند
و امکان تلاش مجدد می‌دهد. خطای تنظیمات Core و بررسی حساب بازخورد آشکار دارد.
چیدمان اصلی هنگام بررسی حساب یا خطای موقت محتوای محافظت‌شده را پنهان می‌کند.
صفحه‌های کسب‌وکار شکست خواندن را از پاسخ موفقِ خالی جدا می‌کنند و دادهٔ
پذیرفته‌شده را پس از شکست بازخوانی حفظ می‌کنند. خطای تغییر داده متعلق به همان قابلیت
می‌ماند. چرخهٔ مشترک تغییر داده و حفاظت رکورد، نشست و مجوز در
[صفحه‌های مدیریتی](business-screens.fa.md) توضیح داده شده است.

Core تابع `acceptSettings` را ارائه می‌کند؛ جایگزینی snapshot خواندن، کار اولیهٔ
قدیمی را پیش از اعمال زبان، لوگو و رنگ‌های پذیرفته‌شده بی‌اعتبار می‌کند. شکست اولیه
با امکان تلاش مجدد آشکار است. ویرایشگر تنظیمات دادهٔ پذیرفته‌شده و
اعتبارسنجی‌شده می‌دهد و این رفتار را حفظ می‌کند.
فقط ترجیحات پوسته و فشردگی در مرورگر ماندگار می‌شوند. زبان فعال، جهت، تقویم و
نام‌ها متعلق به API هستند و تا دریافت تنظیمات پذیرفته‌شده، آغاز ثابت فارسی است؛
انتخابگر زبان بازدیدکننده وجود ندارد.

## نسل ورود و خروج

حافظهٔ اعتبارنامه، نسل پایدار ورود و خروج را دنبال می‌کند. refresh توکن برگشتی را
بدون تغییر نسل در حافظه قرار می‌دهد و توکن برگشتی اعتبارسنجی می‌شود. این رفتار
کلاینت، ذخیره‌سازی نشست، ابطال یا چرخش توکن در API را ثابت نمی‌کند. درخواست وابسته به نشست، نسل زمان ارسال را نگه می‌دارد، پیش
از تکرار ۴۰۱ دوباره می‌سنجد و پاسخ موفق یا خطای متعلق به نسل قبلی را لغو تلقی می‌کند.
تغییر دادهٔ قدیمی، حتی بدون signal، نمی‌تواند با bearer حساب تازه تکرار شود یا
پروفایل قدیمی را وارد نشست تازهٔ فرانت‌اند کند. فقط خواندن عمومی **GET/HEAD /settings**
مستثنا است؛ `/languages` به احراز هویت نیاز دارد و مانند `PUT /settings` وابسته به
نسل نشست است. پاسخ احراز
هویت نیز به نسل وابسته است تا ورود قدیمی نتواند اعتبارنامهٔ تازه را جایگزین کند.
توابع `login`، `register`، `forgotPassword` و `requestOtp` بدون تغییر محتوای درخواست،
`AbortSignal` اختیاری می‌پذیرند. ورود و ثبت‌نام پیش از ثبت توکن اعتبارسنجی‌شده دوباره
لغو را بررسی می‌کنند، حتی اگر آداپتور پس از abort تکمیل شود. فرم‌ها کار جایگزین‌شده
یا متعلق به مؤلفهٔ بسته‌شده را لغو و نتیجهٔ قدیمی را نادیده می‌گیرند.

خروج‌های هم‌زمان یک نسل، درخواست مشترک دارند و فقط همان نسل را پاک می‌کنند. Layout
از کلیک تکراری خروج جلوگیری و تکمیل پس از unmount یا ایجاد توکن غیرخالیِ ورود تازه
را نادیده می‌گیرد. این رفتار با پاک‌کردن توکن توسط خروج معتبر سازگار است.

این محافظ‌ها از وضعیت فرانت‌اند و تکرار درخواست حفاظت می‌کنند. لغو نمی‌تواند تغییر
قبلاً ثبت‌شدهٔ سرور یا اثر کوکی در مرورگر را برگرداند. قواعد احراز هویت، مجوزدهی،
تراکنش و ابطال نشست در API همچنان مرجع نهایی هستند و به بررسی جداگانهٔ API نیاز دارند.

برای ساخت کاربر و بازنشانی گذرواژه، تأیید موفق API باعث حفظ رمز تولیدشده برای
اعلان سطح برنامه در همان نسل ورود آغازکننده می‌شود. جداشدن مؤلفه، تغییر محدوده یا
لغو، این رمز تأییدشده را حذف نمی‌کند. تغییر نسل ورود مانع نمایش اعلان می‌شود؛
حالت قدیمی فرم، جابه‌جایی مسیر و پیام خطای عادی همچنان محافظت می‌شوند. اگر پاسخ
HTTP لغو شود یا ناموفق باشد، نتیجهٔ سرور نامعلوم است و موفقیت قطعی تغییر گذرواژه
اعلام نمی‌شود.

شکست نهایی refresh در کلاینت فقط اعتبارنامهٔ حافظه و نشست رابط مدیریت را منقضی
می‌کند؛ به‌خودی‌خود نشست‌های سرور را باطل نمی‌کند. ابطال نشست در تغییر یا بازیابی
گذرواژه و خروج صریح، همچنان متعلق به API است.

## اصلاح تاریخی پس از خط مبنا — ۲۴ اکتبر ۲۰۲۶

ارزیابی تاریخی آزمایشی فهم کد دو شاخهٔ کلاینت را شناسایی کرد: خواندن احرازشدهٔ
`/languages` به‌اشتباه از ثبت نسل مستثنا بود و پاسخ ۴۰۱ بدون config یا شناسهٔ نسل،
نسل فعلی را فرض می‌کرد. هر دو پس از آن خط مبنا اصلاح شدند. چنین خطاهایی دیگر
refresh را آغاز یا ورود نامرتبط را پاک نمی‌کنند؛ خطای خواندن عمومی تنظیمات نیز
همین رفتار را دارد. آزمون متمرکز، پاسخ دیررس زبان‌های نشست قدیمی، نبود config یا
نسل، ۴۰۱ تکرارشدهٔ بدون نسل و ۴۰۱ تنظیمات عمومی را پوشش می‌دهد. پوشش refresh در
همان نسل، یک بار تکرار، انقضای نهایی و لغو حفظ شده است.

## بررسی و آزمون جداشده

آزمون‌های واحد منتشرشده با loader و fixture ساختگی Core، چیدمان و فرم و Axios/MSW،
تکمیل قدیمی، cleanup و بازخوانی، لغو بدون جایگزین، تنظیمات قدیمی در برابر snapshot
پذیرفته‌شده، StrictMode، تلاش مجدد خطای اولیه، حفظ داده پس از شکست بازخوانی، بازیابی
timeout، refresh مشترک، نسل ورود، لغو احراز هویت و خروج را پوشش می‌دهند. دادهٔ مالک
یا سرویس در حال اجرا لازم نیست. اصلاح تاریخی بالا زمینهٔ تصمیم است و گزارش تازهٔ
بررسی برنامهٔ کامل نیست.
[پروژهٔ جداگانهٔ Storybook](storybook-verification.fa.md) مالکان API قابلیت‌ها و
کلاینت مشترک HTTP را با mock ساختگی کامل جایگزین می‌کند. سناریوهای واقعی Chromium،
بررسی‌های تعاملی مؤلفه را اجرا می‌کنند و با نقض دسترس‌پذیری شکست می‌خورند؛ این
آزمون‌ها اتصال API بیرونی یا مسیر کامل برنامه را ثابت نمی‌کنند.

از [فهرست مرجع](../.agents/validation.json) استفاده و پیش از کامیت یا تحویل PR
مجاز، `npm run validate -- full` را روی خروجی جداگانهٔ همان نسخهٔ دقیق پیشنهادی اجرا
کنید. هر یازده بررسی، از جمله ساخت واقعی و ایستای Storybook و سناریوهای Chromium،
الزامی باقی می‌مانند. پس از `npm ci` و پیش از دستور کامل مرجع،
`npm run browser:install` را اجرا کنید. Vitest کشف فایل محیط را غیرفعال و مقدارهای
ساختگی را صریح تعیین می‌کند؛ وضعیت خصوصی را نخوانید و API توسعه، اعتبارنامه یا
دادهٔ واقعی را fixture قرار ندهید. شواهد ساخت نهایی برنامه، مسیر سرتاسری کامل،
کارایی میدانی و تصویر متعلق به مرحلهٔ قابل اجرا با هر نوزده بررسی واقعی برنامه هستند.
[سیاست انتشار](bootstrap.fa.md)، [مالکیت HTTP](http-client.fa.md)،
[چرخهٔ درخواست](request-lifecycle.fa.md) و [مالکیت Core و احراز هویت](core-auth.fa.md) را ببینید.
