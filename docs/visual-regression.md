# Application visual comparison and provenance

[English](visual-regression.md) · [فارسی](visual-regression.fa.md)

The four PNGs and `metadata.json` in `e2e/visual/baselines/win32` are retained provenance. Metadata records generation on 2026-10-24 and a historical review on 2026-10-26 for its own source fingerprint, Win32/x64, Node, Playwright and bundled Chromium versions. Preserve those bytes and dates. Its recorded `reviewed` status is not approval of the current source, a new screenshot comparison or a portable cross-platform baseline.

Read the [publication policy](../.github/bootstrap-policy.json) and [validation manifest](../.agents/validation.json) before assuming application verification is admitted. The application phase uses the real visual runner and browser fixtures, while the isolated [Storybook suite](storybook-verification.md) remains separate component evidence. A declared phase or configured job alone does not establish an executed comparison.

`npm run test:visual` compares without updating. New application baselines are separate from history under `e2e/visual/baselines/application/<platform>`. Their metadata must record the actual platform, architecture, OS release, Node, locked Playwright, bundled Chromium, source inputs/fingerprint and generation time, plus explicit human review of every image. The runner rejects pending review or a runtime mismatch before fixtures run. Local Windows desktop captures cannot approve Windows Server CI images.

Source provenance fingerprints the explicitly admitted `src/` and `public/` inventory, including application composition, providers, styles, fonts and shared controls, together with the build configuration and visual fixture/runner inputs. Image baselines and operator environment files are not source inputs. The finite sorted list and length-delimited bytes bind every capture to its recorded public source; legitimate later source changes are assessed by the unchanged image comparison rather than silently reusing a current-source approval claim.

The six scenarios cover English/light desktop login, Persian/dark mobile login, the English/dark role drawer, a Persian/light user list with an inactive second account, and English/light recovery and registration forms. They wait for API-derived language/direction and palette, loaded local fonts and no request-error alert. Every external API request uses an explicit synthetic handler; unexpected requests fail. Screenshot thresholds, zero retries and owned strict loopback previews are preserved.

`npm run test:visual:update` requires explicit authorization and creates a new pending capture directory under `coverage/visual/captures`; it does not overwrite approved or historical baselines. Updates are forbidden in CI. Result metadata, failure traces and HTML reports stay under `coverage/visual`. A process lock prevents overlapping visual builds, and occupied fixture ports fail before contacting another service.

Capture success is not approval. Failed or partial captures remain pending; neither assistant observation nor a publication request supplies human review. Before promotion, present the exact image bytes and runtime/source metadata for actual human approval. Preserve the first failure artifacts and existing historical bytes/dates. An automated capture on another runtime requires its own expressly authorized workflow; do not bypass the CI update prohibition or silently relax provenance.

See [accessibility](accessibility.md), [test reliability](test-reliability.md) and [validation](validation.md). Screenshots do not establish API-provider compatibility, assistive-technology review or deployed behavior.

Comparison verifies the approved PNG inventory and every recorded SHA-256 before launching a browser and again after the child completes, before writing a comparison result. Ordinary Windows 8.3 path spellings are canonicalized only after every directory ancestor passes the no-link check; linked directories and images remain rejected. Comparison and capture both verify the source fingerprint and input list again after the child build/capture; a source change rejects the result and leaves new captures pending. CI rejects snapshot-update flags in both long and `-u` shorthand forms.
