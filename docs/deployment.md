# Static hosting preparation

[English](deployment.md) · [فارسی](deployment.fa.md)

The current `assistant-guidance` phase intentionally adds finite deployment and quality prerequisites while retaining `applicationReady: false`. Templates, validators, packaging helpers and synthetic tests are available; an application entry point, production build, real Docker run and deployed checks are not current verification.

[Public configuration validation](../scripts/validate-deployment-env.mjs) checks an exact API origin, a safe slash-terminated base path, an immutable release ID and optional public observability URL. HTTPS is required except for explicit HTTP loopback. These browser-visible values must contain no credentials. The separate API must independently authorize requests and allow the actual admin origin.

[Template rendering](../scripts/render-deployment.mjs) accepts an explicit template and configuration object, normalizes a valid string `ADMIN_HOST` to lowercase, validates bare DNS host/port/path fields and substitutes only declared public placeholders. Its CLI uses `--template`, `--config-file` and `--output` with relative paths beneath the working directory, rejects traversal and symbolic links, reads the selected ordinary input files and creates a new output exclusively. The `--config-file` name avoids Node's `--env-file` preload behavior, so validation happens before configuration is read. Do not invoke it on real operator files during source verification. The three reviewed public example paths are synthetic; arbitrary environment files remain private.

[Packaging](../scripts/package-release.mjs) requires a completed `dist` tree and matching build metadata. It checks release identity, base/origin and path containment, refuses symbolic-link assets and existing release output, and omits disallowed asset names. Synthetic packaging fixtures verify those rules; they are not a production artifact or a secret-content audit.

Future authorized activation must first publish and validate the application build and its genuine browser/visual gates. Then package one immutable identity, render a new Nginx configuration, provision TLS privately, validate the intended host and switch only the verified release. Docker/Compose likewise depends on that future build. Its Nginx process uses an unprivileged user and internal ports 8080/8443, with all capabilities dropped and writes confined to `/tmp`; provision readable TLS key ownership outside the image and mount it read-only. Run the network [health helper](../scripts/healthcheck.mjs) only against an explicitly authorized target; no deployment, DNS, TLS or availability result is implied here.

The health helper's CLI accepts `TARGET_URL [EXPECTED_RELEASE [BASE_PATH]]`; its function accepts the same three arguments. Omission of the target retains `http://127.0.0.1/`; an explicit `null` is invalid. An explicitly empty expected release fails before any request. The target must use HTTP(S) without credentials, query or fragment. An HTML-only probe can target a route. With an expected release and no explicit base path, the target declares the application's canonical slash-terminated base URL; the helper does not infer a base from an arbitrary SPA route. To probe a deep route, supply the configured base path: `/console/auth/` or `/console/auth/register` with `/console/` requests the document first and then `/console/_kernel/release` on the same origin. Nested bases such as `/team/admin/` work the same way. The base must be `/` or canonical slash-delimited segments ending in `/`, and the route must remain beneath it. Invalid targets and bases fail before any network request; redirects remain errors.
